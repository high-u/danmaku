# Issue #27 改修計画: X11 オーバーレイ実装の整頓

対象: `apps/danmaku-linux/src/main.rs`

## 目的（確定）

X11 オーバーレイ実装を、**API の抽象度を揃え、役割をきれいに分断する**。
小さなプログラムであり、レイヤードアーキテクチャの導入や将来拡張のための
抽象化は**しない**。「今あるコードを、役割が見えて抽象度の揃った素直な形に
整える」ことがゴール。

到達状態:

- **中核**（弾幕の生成・描画・socket 受信）は「どんなオーバーレイが欲しいか」
  という意図だけを語る。生 xlib の手続きを直接持たない。
- **その意図が、このマシンで実際に正しく効いている。**
- X11 固有の手続き（EWMH / atom 操作 / XMoveWindow / FFI）は役割ごとに
  1 か所へまとまっている。

## スコープの線引き（重要）

| | 扱い |
|---|---|
| 抽象度を揃え役割を分断する整頓 | **含む** |
| 「意図を宣言しているのに効いていない」不備の解消（例: `_NET_WM_STATE` が乗らない） | **含む**。これは特定 DE の問題ではなくアプリ自身の設計不備。在るべき姿に直す過程で正す |
| 検証環境 | **このマシン**。XFCE/Xvnc コンテナではない |
| 特定ディストリビューション/DE への個別互換対応 | **含まない**（本 Issue 完了 → macOS 追従の後） |
| Wayland バックエンド実装 | **含まない**（拡張前提の構造も作らない） |
| 弾幕の描画/速度/レーン等の仕様変更 | **含まない** |

補足: 観測事実（`xprop _NET_WM_STATE` が `not found`、`wmctrl -l` に列挙される）は
たまたま XFCE で表面化しただけで、XFCE 依存ではない。「宣言した意図が効いていない」
というアプリの不備の現れであり、在るべき姿に整える対象。

## 決定基準（なぜ在るべき姿か）

高レイヤー（GTK/GDK）の API は、WM・コンポジタ・ディストリビューションの違いを
ライブラリ側が吸収する。生 xlib は EWMH 手順や atom 操作をアプリに直書きするため、
環境やバージョンが変わると壊れやすく追従コストが上がる。よって:

> **実際に効く範囲で、可能な限り高いレイヤーを採る。低レイヤー（生 xlib）へ
> 落とすのは、高レイヤーでは効かないと検証で確認できた場合に限り、その理由を記録する。**

狙いは、今後の Ubuntu 含む各ディストリビューションのバージョンアップ時に、なるべく
高レイヤーで綺麗な実装にしておくことで対応箇所を減らし、追従を楽にすること。
（＝ DE 名やディストロで分岐しない。違いはライブラリに吸収させる）

## 設計の前提（全フェーズ共通）

- **過剰設計しない。** trait による抽象化や差し替え前提の層は作らない。
  X11 の手続きを「置く場所」をまとめる程度に留める。
- **置き場は up-front に設計しない。** 項目を検証して移すたびに、置き場
  （例: X11 手続き用モジュール）が自然に育つ形にする。空の箱を先に作らない。
- 各フェーズは **このマシンで挙動が現状から劣化していないこと** を確認して締める。
  1 フェーズ ≒ 1 コミット相当。
- **仮説と現実が食い違ったら現実優先。** 食い違いは記録し計画に反映する。

## 進め方

各フェーズで以下を回す:

1. **検証** — なぜ今この抽象度・この手順なのかをこのマシンで確かめる。
   （現コードは試行錯誤の末の形であり、不自然に見えても理由がある前提で読む）
2. **選択** — このアプリにとって在るべき実装を決める（抽象度を上げる/現状維持/置き場へ移設）。
3. **改修** — 最小で行う。
4. **確認** — Phase 0 の期待値表と照合し、挙動不変（または意図どおり改善）を確認。

### 検証手順（各フェーズで再利用する）

1. オーバーレイ起動: `cargo run -q -- send "<文言>"`
2. ウィンドウ特定: `_NET_CLIENT_LIST` を走査し `WM_CLASS` が `"danmaku"` のものを採る
3. EWMH 状態: `xprop -id <win> _NET_WM_STATE _NET_WM_DESKTOP`
4. 配置: `xwininfo -id <win>` の Absolute X/Y・Width/Height
5. クリックスルー: `xdotool mousemove <領域中心>` → `xdotool getmouselocation --shell`
   の `WINDOW` が **danmaku 自身でなく背後**を返せば素通り＝OK（自身を返したら劣化）
6. 透過: 目視
7. 後始末: `pkill -f 'target/debug/danmaku serve'`

### Phase 0 計測結果（danmaku ウィンドウの実態）

`xprop`/`xwininfo` で稼働中ウィンドウ（WM_CLASS=danmaku）を計測した実態:

### Phase 0 で判明した中核の手がかり（Phase 3 で正す）

`set_x11_initial_wm_state` は 4 状態（ABOVE/STICKY/SKIP_TASKBAR/SKIP_PAGER）を
realize 時に XChangeProperty でまとめて設定している。だが実際に残るのは **ABOVE だけ**。

- realize 時の XChangeProperty は **map 時に Mutter にリセットされ効かない**。
- ABOVE のみ map 後 `send_x11_state_change_above` の ClientMessage で**再送**され復活。
- **残り 3 状態は再送していない**ため黙って消える。

→ これが「なぜ map 後に再通知しているか」の実機的な答え。現状は「ABOVE は
ワークアラウンドで生存／他 3 つは喪失」という、まさに『宣言したのに効いていない』
設計不備。**修正は Phase 3。**（高レイヤー手段で全状態を確実に効かせられるかを Phase 3 で検証）

## Phase 1: 最前面・全 WS・skip taskbar/pager（生 xlib `_NET_WM_STATE`）— 骨格

本 Issue の中心であり**在るべき姿の骨格**。生 xlib が最も中核に癒着しており、
ここで「X11 手続きの置き場」「意図と機構の境界」「意図の宣言面」が決まる。
他項目はこの骨格に合わせて乗るので、**最初にやる**。

- 対象: `set_x11_initial_wm_state` (556-580)、`send_x11_state_change_above` (582-619)、
  および共有基盤の `x11_handles` (540-554) / `atom` (646-649)
- 検証（実コードで試して観察する）:
  - なぜ realize で初期設定し、map 後に ClientMessage で再通知しているのか
    （Phase 0 で「初期設定は map 時にリセットされ ABOVE のみ再送で生存」と判明済み）。
  - 宣言した各状態を、GTK/GDK の高レイヤー API で表現したとき実際に効くか
    （= 決定基準どおり、効くなら高レイヤーへ。効かない部分だけ生 xlib に残す）。
- 選択: 中核には意図だけを残し、必要な X11 手続きは置き場へまとめる。
  **観測挙動はこのマシンで不変が条件**（Phase 0 ベースラインと照合）。
- 影響が大きいため、**検証結果が出た時点で改修方針を一度すり合わせる。**

## Phase 2: 指定モニタ中央配置（生 xlib `XMoveWindow`）

骨格（X11 手続きの置き場・`x11_handles` 共有）が決まった上で、それに乗せる。

- 対象: `move_to_monitor_center` (630-644)、`monitor_for_screen` (621-627)
- 検証: GTK/GDK にモニタ指定配置の手段が本当に無い/効かないのかをこのマシンで確認。
- 選択: 代替できれば高レイヤーへ。できなければ生 xlib のまま Phase 1 で作った置き場へ。

## Phase 3: クリックスルー（GDK）

骨格で決めた意図の宣言面に合わせて表現する。

- 対象: `surface.set_input_region(空)` (301-306)
- 検証: GDK のままが妥当か。Phase 1 の意図 API に含めるか中核に残すか。

## Phase 4: 枠なし・透過背景（GTK）

- 対象: `.decorated(false)` (255)、CSS 透過 (259-273)
- 既に高水準。中核に残すか/意図側へ寄せるかの**役割の置き場所判断**。
- **Phase 0 の課題を持ち込む**: `_NET_WM_CM_S0` が not found なのに透過は
  効いている。アプリが「コンポジタが要る」と思い込んでよいか、思い込むなら
  何を見て判断するのが正しいかを検証する（誤った前提を埋め込まない）。

## Phase 5: 中核の最終点検

- Phase 1〜4 の結果、FFI/生 xlib の詳細が中核から消え置き場の内部に隔離され、
  中核 `build_ui` が意図だけで読める状態になったかを点検（合格条件）。

## Phase 6: 命名・コメント・ドキュメント整頓

- 役割が名前で分かるよう命名統一。各「なぜこの形か」の検証結果を
  コメント/ドキュメントに反映。

## フェーズ別チェック（挙動維持の基準: このマシン）

各フェーズ末で、Phase 0 の期待値テーブルと照合:

- 透過が保たれている
- クリックスルーが効く
- 最前面が効く
- 全ワークスペースに表示される
- 指定モニタ中央に配置される

劣化があれば次フェーズへ進まない。Phase 3 以降は「意図どおり改善できたか」も併せて確認。
