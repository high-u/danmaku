# 常駐アプリの存在認識 — 選択肢メモ (danmaku-linux)

## このドキュメントの位置づけ

- **対象は Linux のみ** (macOS は対象外)。
- **現状の決定: 何もしない (= 選択肢 A)。** 認識手段は今は実装しない。
- このファイルは「ユーザーに danmaku が起動中だと認識させる手段」の**今後の選択肢を残す**ためのもの。
- ファイル名は `TRAY_DESIGN` だが、対象はトレイに限らない (トレイは選択肢 D の一つ)。

## 前提 (重要)

- danmaku の overlay は **透過・クリックスルー・skip-taskbar / skip-pager** 指定で、
  **アイドル中は画面に何も出ない**。「起動しているのに気づけない」のが本質課題。
- **現在の実装は「正」ではない。** クリックスルー・窓を持たない等は今の都合であって
  固定の制約ではない。選択肢によっては設計を変えてよい (特に C)。

## ライブラリ選定の基準 (この順で判断する)

1. デファクトスタンダードか / 人気があるか
2. 枯れているか、または活発にメンテされているか
3. そもそも標準機能 (std) / 既存依存でシンプルに実現できないか
4. (その後で) 機能的観点 — 過不足・推移的依存の重さ・アーキテクチャ適合

## 選択肢 C: タスクバーに大きいアイコンで出す

「通常のデスクトップアプリ」として提示する案 (トレイより大きいアイコン)。

### 成立条件: 普通のウィンドウを 1 枚持たせる

- 窓を持たないままだと、アイコンを押しても何も起きず噛み合わない。
- **ステータス窓 or 設定画面を 1 枚持たせる**と「アイコン → クリック → 窓が出る」という
  デスクトップアプリの標準ループが成立し、体裁が整う。
- 構成は二層: **操作対象 = 普通の窓 (ステータス/設定)** + **出力 = 透過オーバーレイ**。
- 窓はフル設定でなくてよい。「起動中表示 + 終了ボタン」程度のステータス窓でも可。

### 実現方法

- overlay 窓とは別に通常窓を出す。タスクバー表示は `_NET_WM_STATE_SKIP_TASKBAR` を
  **付けない**窓を用意する。

### 注意点 (Linux のタスクバーは窓単位)

- **タスクバーのエントリは窓単位**。窓を閉じるとタスクバーからも消える。常駐感を保つには
  ステータス/設定窓を**出しっぱなし (または最小化で保持)** する必要がある。

### 評価

- ✓ 「アプリが在る」感は最も強い。alt-tab にも出る。
- ✗ **danmaku を「窓を持つ通常アプリ」に作り替える設計変更**が前提 (依存追加は不要)。
- 新規依存: ゼロ (フラグ + 窓の実装)。

## 選択肢 D: トレイ常駐 (小さいアイコン)

「窓を持たない常駐ユーティリティ」の王道。まさにこの UI 領域はそのための場所。

### ③ そもそもクレート無しで済むか → 済まない

- **GTK4 に system tray API は無い。** `GtkStatusIcon` は GTK3.14 で非推奨化され GTK4 で削除。
  GTK 公式も「通知 API か、プラットフォーム固有 API を使え」と明言。よって gtk4 単体・std
  では不可能で、クレートが不可避。

### ① 人気・② メンテ (crates.io 実数, 2026-06 時点)

| crate | 総DL | 直近DL | 最新版 / 更新 | 方式 | メンテ |
|---|---|---|---|---|---|
| tray-icon | 15.2M | 6.5M | 0.24 / 2026-05 | libappindicator(**GTK3**) ラップ | 活発 (Tauri 製) |
| ksni | 886K | 254K | 0.3.4 / 2026-04 | 純 SNI を D-Bus 直接 | 活発 |
| tray-item | 151K | 17K | 0.10 / 2024-04 | appindicator ラップ | 停滞 |
| libappindicator | 14.2M | 5.2M | 0.9 / 2023-10 | C ライブラリ薄ラッパ | 古い |

### 決定打 (本アプリは GTK4) → ksni

- ①だけ見れば筆頭は **tray-icon** (DL も活発さも上、デファクト)。
- だが tray-icon は **GTK3 + libappindicator3 + libxdo の system ライブラリ**を要求し
  GTK の event loop 前提。本アプリは **GTK4**。→ GTK3/GTK4 の system 依存同居となり
  「単一バイナリ・疎結合」と衝突。配布も C ライブラリ前提が増える。→ **脱落**。
- **ksni** は GTK も libappindicator も要求せず SNI を D-Bus (zbus) で話すだけ。GTK4 に
  干渉せず別スレッドで回せる。→ **採用候補は ksni** で確定。

### 評価

- ✓ 常駐ユーティリティの王道。終了などの操作も置ける。違和感がない。
- ✗ ksni は **zbus / tokio を推移的に引く** (SNI トレイのコスト。④の話。許容と判断)。
- 新規依存: ksni。

### 採用時の確定事項

- **トレイ crate: `ksni`** (`--features blocking`)。glib メインループと干渉しないよう
  自前スレッドで回す。
- **終了動作: `std::process::exit(0)`**。既存の「SIGTERM 即終了・socket は次回掃除」方針と
  一致し、終了経路を 1 本に揃えられる。スレッド間チャネル等の追加プラミング不要。
  - 懸念 (許容済み): デストラクタを飛ばすので socket ファイルは残るが、次回起動時に
    `ensure_socket_available` が掃除する (= 既存 SIGTERM 経路と同挙動)。将来「終了時に
    後始末が必要」になったら exit(0) では不可なので作り直しになる、という前提だけ留意。
- **アイコン供給方法: (a) ビルド時 raw 化**。`icon.png` を ARGB へ事前変換し
  `include_bytes!` で焼き込む。実行時のデコード依存 (`png` / `image`) を持たない (③重視)。
  - サブ選択 (実装時に決める):
    - a1: 事前生成した raw ARGB を blob としてコミット (真の依存ゼロ。ただしリポジトリに
      不透明バイナリが入る)
    - a2: `build.rs` で `icon.png` をビルド時変換 (`png` は **build-dependencies** のみ。
      最終バイナリの依存には乗らない。リポジトリには PNG が残り blob を持たない)
- **コード配置**: トレイ実装は `src/tray.rs` に隔離し、`main.rs` 追加は `tray::spawn();` の
  1 行のみ。アイコンは構造体フィールドに 1 個持つ (グローバル static にしない)。

### 未確定 (今詰めない): アイコン素材

- サイズ: 48x48 1 枚 / 複数サイズ (16・22・32・48 等) を持つ

## 選択肢 E: 起動 / 終了時のデスクトップ通知

- 通知 API は実在する: freedesktop の Desktop Notifications 仕様
  (D-Bus `org.freedesktop.Notifications`)。GLib 標準の `GNotification` (gio) で出せる。
  **gio は既に使用中 → 新規依存ゼロ**。
- ✓ 「起動した」を確実に伝える。軽い。
- ✗ **一過性**。「今も動いてる」を持続させない。E 単体では常駐感を満たさず、A や C への
  添え物向き。優先度は最下位。
- 新規依存: ゼロ (gio 既存)。
